## The finding in one line

A file whose on-disk bytes are provably correct was being returned from the
Linux page cache with one byte wrong, bit 6 cleared. Evicting the page cache
made it correct again. The storage was never wrong; RAM was.

## The decisive observation

Size: 17,923,394,624 bytes. Upstream sha256 (unsloth LFS oid):
`bee238bbeb3dc0a34bde4d0dedbaee1f98c009e8bb4226f03070054c12fb1372`

The disk never changed. Evicting RAM fixed it. That is a memory fault.

## Why this matters more than the three earlier events

The three corruptions found on 2026-08-14 all had page-cache and `O_DIRECT`
reads *agreeing* — the bytes were genuinely wrong on the platter, i.e. written
wrong. This one is the opposite: storage provably correct, RAM wrong. Storage
cannot be the cause of a fault that appears only in a cached copy of a file
whose disk bytes are intact.

It is also the fault that memtester and memtest-style scans cannot reach.
Those test pages the kernel hands the test process; they never test the page
cache holding a 17 GB file.

## What is NOT known

- **Physical address was not obtainable.** `/proc/self/pagemap` returns the
  entry with PFN masked to 0 (`0xa180000000000000`, present=1, PFN=0) because
  reading real frame numbers needs `CAP_SYS_ADMIN`. `/proc/kpageflags` and
  `/proc/kpagecount` are not readable either. Without root there is no way to
  turn the virtual page into a physical address, so no targeted memtest86+
  range can be derived from this session.
- **Which DIMM.** Four identical Samsung M378A2K43DB1-CTD 16GB non-ECC in
  ChannelA-DIMM0/1 and ChannelB-DIMM0/1. Nothing here localises the fault to
  one of them.
- **Whether it is progressive.** Four events over ~11 days is all the history
  there is.

## How to re-test after the reseat

The exact method that caught it, in order:

1. Read the file normally and hash it:
   `sha256sum ~/Desktop/qwen3.8-27b-gguf/Qwen3.8-27B-UD-Q4_K_XL.gguf`
   Expect `bee238bb…`.
2. Read the same file with `O_DIRECT` and hash it. If the two disagree, the
   page cache is corrupt and the disk is fine — repeat of this fault.
3. If they disagree, diff cached against direct chunk by chunk to locate the
   byte, and record offset, both values, XOR, bit index, and `offset % 4096`.
   Script: `scratchpad/cache_vs_disk.py` (session b6d2cbb1), reproduced in the
   appendix below.
4. Watch specifically for `offset % 4096 == 2309` and `xor == 0x40`. A fifth
   occurrence at that intra-page offset after a reseat would mean the reseat
   did not fix it.

**Capture the physical address next time, as root, before touching anything:**
with root, re-run step 2's mmap and read `/proc/self/pagemap` for the mapping's
virtual page; the PFN will be populated, and `PFN * 4096 + (offset % 4096)`
is the physical byte address. That number is what makes a targeted memtest86+
range possible instead of an overnight full pass.

## Appendix — the reproducer

```python
# cached vs device, locate every differing byte
import mmap, os
P = "<file>"; CH = 1 << 22
fd_d = os.open(P, os.O_RDONLY | os.O_DIRECT)
f_c = open(P, "rb", buffering=0)
buf = mmap.mmap(-1, CH); size = os.fstat(fd_d).st_size; off = 0
while off < size:
    n = os.preadv(fd_d, [buf], off)
    if n <= 0: break
    disk = bytes(memoryview(buf)[:n]); f_c.seek(off); cache = f_c.read(n)
    if cache != disk:
        for j in range(n):
            if cache[j] != disk[j]:
                print(off + j, hex(cache[j]), hex(disk[j]),
                      hex(cache[j] ^ disk[j]), (off + j) % 4096)
    off += n
```

Eviction, to clear a corrupt cached copy without a reboot:

```python
import os
fd = os.open(P, os.O_RDONLY)
os.posix_fadvise(fd, 0, 0, os.POSIX_FADV_DONTNEED)
os.close(fd)
```
