## N1. Scope, question and claims under test

**Trigger.** Nari Labs' NariQ GGUFs of Qwen3.8-27B (HF `nari-labs/Qwen3.8-27B-NariQ-GGUF`, Hacker News front page
2026-11-24) claim "BF16-level" quality in a 10.12 GB file. The method is trellis-coded post-training quantization
(arXiv 2611.26157, Doyeob Kim, Nari Labs, v1 2026-11-19). The files need Nari Labs' llama.cpp fork
(`nari-labs/nari-llama.cpp`), because they use new tensor types that upstream hasn't assigned (GGUF type ids 44-49).

**Why a 3060.** The 3.0 bpw file is the first 27B dense file that fits a 12 GB card with the quality claim attached. Its
same-size stock comparison, Unsloth's UD-IQ3_XXS (10.93 GB), is the file the card and the paper compare against.

**Question.** On a 12 GB Ampere GeForce card, which the fork has not tested, what decode and prompt-processing speed do
NariQ 3.0 and 2.5 bpw get on the fork, against UD-IQ3_XXS on the fork and on mainline at the fork's own base commit?

**Claims under test (the fork's own words):**
- **F1:** "On Ampere, Ada, Hopper and Apple GPUs, NariQ files decode slower than comparable stock GGUFs for now."
  (release `b12431-nariv0`, Known limits). Tested as: F-N3 decode slower than M-IQ3 decode.
- **F2 (implicit in the fork's description, "upstream b12431" plus NariQ additions):** the fork leaves stock files alone.
  Tested as: F-IQ3 and M-IQ3 decode and prompt processing show no difference.

**Not under test here:** quality. Nothing in this part measures KLD, PPL or task scores. The authors' "BF16-level"
figures are task scores (DeepSWE, Terminal-Bench 2.1, AIME, MGSM, RealWorldQA) plus KL at model-written agent tokens.
Our quality measurement is section T, on Tamanna.

## N5. Measurements

**Per arm (as in the MoE cache lock, M5):** start the server and wait for `/health`. Then one **cold request** (512-token
prompt, its own nonce), **reported separately and excluded from every cell value**. Then **3 measured requests at 512
tokens, then 3 at 4,096**, on the same resident server. **Cell value = median of the 3 (min..max).**

Each request is a chat completion, streamed, with a fresh 8-hex nonce line first. Settings: thinking off
(`enable_thinking: false`), temperature 0, `cache_prompt false`, `ignore_eos`, `max_tokens 256`.

- **Prompts:** `prompt-512.txt` and `prompt-4096.txt`, cut from the HotRod corpus by the MoE cache record's
  `cut_prompts.py` (median of 16 fixed nonces), on **the IQ3 file's tokenizer with the mainline build's
  `llama-tokenize`**, so each request's prompt_n is 512 and 4,096. The NariQ GGUFs' tokenizer and chat template are
  compared with the IQ3 file's (`gguf` metadata dump: vocab size, merges hash, chat template sha256) before any arm. If
  they differ, the run stops and Mark is told. Prompt files and their sha256 go in the record.
- **Decode** = the server's `predicted_per_second`. **Prompt processing** = `prompt_per_second`, with client TTFT
  beside it.
- **Memory:** card memory.used sampled at 1 s, with peak per cell and per arm, plus the load-time buffer lines from the
  server log. RAM: minimum MemAvailable over the arm, and server VmRSS split into RssAnon and RssFile.
- **Per request, as in HotRod H5:** prompt_n, cache_n, swap-in/out KiB, NVMe read bytes during prefill and during
  decode, PCIe gen/width during prefill, first 200 characters of each answer.
- **Machine state,** once before the first arm: free RAM and swap, driver version, PCIe link at idle and under load,
  `ollama ps`, and CPU time of the `mycoswarm` and `ollama` processes (also recorded before and after every arm).

**Fit probe (reported, not scored), after the four arms:** for F-N3, F-N25 and M-IQ3, the same command with `-c 16384`
and then `-c 32768`. At each: load, one 512-token request, card peak. Reported as loads/answers or does-not-fit, with
the peak. This is the "how much context fits on 12 GB" row.

**Machine conditions.** HotRod's A1 (swap off, `mycoswarm`/`ollama`/update timers stopped) needs sudo on Rushuna, so
it is **not** in force for this run, and that is stated here in advance. Reasons it's acceptable here: every arm sits
fully on the card; the files are a third of Rushuna's RAM; and swap-out above 0 still voids a request (N6). What's
recorded instead: swap state, `ollama ps` (it must show no model loaded, or the arm doesn't start), and the CPU time of
both daemons around each arm. If a daemon used more than 5 CPU-seconds during an arm, the arm is flagged in the
record, but not voided.

**Memory guard:** `memwatch.py` v3 from the MoE cache record, unchanged, run with `--count-swap`: only the 2 GiB
MemAvailable floor stops a run. On a trip it SIGTERMs the harness and every process named exactly `llama-server`, and
writes `TRIPPED`. The card must read ≤ 50 MiB before every arm.

## N6. Void rules (MoE cache M6, unchanged, with one addition)

A cell is void if any of its 3 measured requests has:
- prompt_n spread over 3 tokens across the 3, or prompt_n differing by more than 3 tokens between arms at the same
  length;
- cache_n above the template header (≈0);
- swap-out above 0 KiB;
- the PCIe link below gen 3 x16 during any prefill;
- NVMe reads over 1 GiB during the decode (flag over 64 MiB);
- an empty, looping or garbled answer (judged on the first 200 characters plus the full text of the 3rd request of
  each cell, which is kept). **Added:** a NariQ answer is judged by the same standard as the IQ3 answer to the same
  prompt. Different wording is fine; incoherence voids it.

An arm is also void if its `/props` build_commit is wrong (N3). A void cell is re-run once (fresh server, its own cold
request, then the cell's 3); void twice is reported as void.

## N7. Predictions (ours, written 2026-11-24, before any build or measurement)

- **F-N3 / M-IQ3, decode: 0.50-0.85x** at both lengths. So **F1 is expected to hold**. On the fork's own tuned card
  (RTX PRO 6000), 3.0 bpw decoded at 0.94x of UD-IQ3_XXS at 4K (88.9 vs 94.7 tok/s), and the fork says Ampere is worse.
- **F-N25 / F-N3, decode: 1.05-1.20x** (the card's PRO 6000 ratio at 4K is 1.12).
- **F-N3 / M-IQ3, prompt processing: 0.30-0.80x.** The fork says its CUDA kernels are "tuned for single-token decode".
- **F-IQ3 vs M-IQ3: no difference shown** on decode or prompt processing, at both lengths. So **F2 is expected to hold**.
- **Fit probe:** F-N3 loads and answers at 16,384 and not at 32,768. F-N25 loads at 32,768. M-IQ3 behaves like F-N3.

## N8. Scoring

- **Faster / slower** only when the medians differ and the min..max ranges don't overlap (HotRod H7). Otherwise "no
  difference shown".
- **F1 holds** at a length if F-N3 decode is slower than M-IQ3 decode. It is scored at 512 and 4,096 separately.
- **F2 holds** at a length and metric if F-IQ3 and M-IQ3 show no difference, or their ratio is inside 0.97-1.03.
  Outside that band with non-overlapping ranges, F2 fails at that length and metric, and the direction is reported.
- **NariQ vs same-size stock, format alone:** F-N3 / F-IQ3 (same build), at both lengths and both metrics, reported
  with ranges. **NariQ vs what a user would otherwise run:** F-N3 / M-IQ3.
- **Our predictions** are scored on the same medians: each ratio inside or outside its predicted band, and the fit
  probe outcomes as hit or miss.

## N9. Limits stated in advance

- One card, one model, two NariQ widths. The fork's kernels are tuned for SM120, so the 3060 result says nothing about
  Blackwell. The fork may well tune Ampere later, and this records `b12431-nariv0` only.
- Speed only. A fast-but-worse or slow-but-better file can't be told apart here. That waits for section T.
- 256-token decodes at short prompts (512 and 4,096) with 3 runs per cell. Long-context decode beyond the fit probe's
  single request isn't measured.
- A1 is not in force (N5). Rushuna is a 4-core i7-7700, and the fork's CPU-side embedding ops may be sensitive to that
  in a way a stronger CPU wouldn't be.
- UD-IQ3_XXS is 0.81 GB larger than NariQ 3.0, so "same size" is approximate. It is the comparison the authors chose.

### T4. Method: KLD, PPL and bits per byte

Tool: `llama-perplexity` at the T2 builds, in its KL-divergence mode (read at b12431,
`tools/perplexity/perplexity.cpp`):
- **Base run:** `--kl-divergence-base FILE` writes the `_logits_` magic, n_ctx, n_vocab, n_chunk, **the token array**,
  then per chunk the log-probabilities of the last 2,047 positions (of 4,096), 248,324 uint16 per position: 0.947 GiB
  per chunk, **about 32.5 GB for 32 chunks**.
- **Arm runs:** `--kl-divergence` reads that file, refuses a different vocabulary size, and evaluates **the stored
  tokens**. Each run reports mean KLD ± SE, KLD percentiles, "same top p", PPL(Q), PPL(base) and mean
  ln(PPL(Q)/PPL(base)).

**Commands** (`harness/kld.sh`; identical across arms except the binary, the file and `-ngl`):

    BIN/llama-perplexity -m FILE -f evalset.txt -c 4096 -b 2048 -ub 512 --chunks 32 -fa on -t 8 --fit off \
        --override-kv tokenizer.ggml.add_bos_token=bool:false -ngl N \
        --kl-divergence-base REF.kld [--kl-divergence]

- **Base run:** mainline, the BF16 file, `-ngl` = the largest value from 8 to 40 that loads and completes one chunk at
  these settings (binary search with `--chunks 1`; each attempt logged; not a measurement).
- **Arms:** `-ngl 99` (every arm file fits the 24 GB card at 4,096).
- `--fit off`: layers are placed as given, never moved by the loader.

**Pinned BOS (Mark's N5 gate decision, 2026-11-24).** Every call passes `--override-kv
tokenizer.ggml.add_bos_token=bool:false`, so no file adds a BOS whatever its metadata says (the IQ3 file lacks the key,
the NariQ files have it False). Each log must show the loader's `Using metadata override … add_bos_token` line; a run
without it is void.

**Token-count match check (a mismatch voids that comparison; `harness/tokcheck.py`).** After the base run, before any
arm: `evalset.txt` is tokenized with `llama-tokenize --no-bos --no-escape` for every pair that runs an arm (IQ3 on
mainline and on the fork, both NariQ files on the fork, R-Q4 on mainline). The first 131,072 ids of each must equal
the token array stored in the base file. A file whose ids differ has every comparison involving it voided, and that
is reported. A mismatch in the reference itself voids the quality part.

**Bits per byte (`harness/bpb.py`).** Scored bytes = the UTF-8 bytes of the 65,504 scored target tokens (positions
2,049-4,095 of each chunk), from the GGUF vocabulary pieces (byte-level BPE, decoded through the inverse
bytes_to_unicode map). Checked first: all stored tokens' pieces must reproduce `evalset.txt`'s matching prefix byte
for byte; if not, bpb isn't reported and the record says so. bpb = ln PPL(Q) × 65,504 / (ln 2 × scored bytes), per
half the same way with that half's tokens and bytes. Dry run on Miu (2026-11-24, tokens from the CPU tokenizer): the
decode matches the prefix; 65,504 scored tokens; **241,010 scored bytes (code 101,008, prose 140,002)**. The bytes
counted are the bytes scored, which settles the perplexity doc's open item 2 for this test.

**Order:** base run → token check → bpb check → arms Q-M-IQ3, Q-F-IQ3, Q-F-N3, Q-F-N25, Q-R-Q4, each once (fixed
build, deterministic). The ± is the tool's SE over the 65,504 scored positions.

**Q-F-IQ3 vs Q-M-IQ3:** the same stock file on both binaries; checks that the fork doesn't change a stock file's
quality numbers, as F2 did for speed.

### T7. Scoring

- **KLD comparisons:** A is "lower" than B when the mean KLD ± 2 SE intervals don't overlap; otherwise "no difference
  shown". The tool's SE treats positions as independent, which understates uncertainty, so the 2 SE margin is
  deliberately wide. Same top-p and PPL ratios are reported beside it, scored only in the ordering predictions.
- **Speed:** N8 (medians, non-overlapping min..max ranges).
- **Predictions:** each band hit or miss on the medians or means; each ordering hit or miss.
- **What this can and can't say about "BF16-level":** the authors' claim rests on task scores and on KL at
  model-written agent tokens, which we don't reproduce. "Lower KLD than R-Q4" would mean closer to the reference than
  our 4-bit file is, on this text; not equal task scores.
