## I5. Arms (all on Rushuna)

**Common llama.cpp server flags (L, U, Q):** `llama-server -m <file> -ngl 99 <placement> -c <CTX> -np 1 -ctk q8_0
-ctv q8_0 -fa auto -t 4 --cache-ram 0 --fit off -lm mmap --jinja --port 8081`, with ubatch and batch at the build
defaults (512 / 2048) unless a cell says otherwise.
- `--cache-ram 0` disables the host prompt cache (default 8192 MiB at the pin). The NariQ record (d9f3d7a7) saw it grow
  ~347 MiB per request even with `cache_prompt false`, and Inkling's experts already take ~17 GB of the 32 GB.
- `-np 1`: one slot, so the whole `-c` belongs to one sequence.
- Q8 KV matches Codacus (11:12). If a build refuses to start with a q8_0 V cache (for example because flash attention
  ends up off), that arm is re-run once with f16 KV. Both the refusal and the substitution are recorded, and the f16
  cells are labelled.
- `-fa auto`: whether FA was actually enabled, and on which device the attention ran, is read from the load log (I6.5).

**Sampling (all arms):** the model's recommended settings, as Codacus used (14:53): temperature 1.0, top-p 1.0, top-k 0,
min-p 0, seed 1234, reasoning at its default. Greedy cells (temperature 0) are marked.

**Requests:** streamed chat completion, a fresh 8-hex nonce line first, `cache_prompt false`, `ignore_eos`,
`max_tokens 256`. Per server: one **cold** request (512-token prompt, excluded from every value), then the cell's
requests.
- **short** = 3 requests with prompt_n 512.
- **deep** = 3 requests with prompt_n ≈ 90% of `-c`: 7,372 at 8K, 29,491 at 32K, 58,982 at 64K. At **256K (262,144),
  1 request at 235,929**, because one prefill at ~175 tok/s takes ~22 minutes.
- Prompts are cut from the HotRod harness corpus (`corpus.txt`, 600,076 bytes), concatenated with itself as needed,
  and counted with each model's tokenizer (`llama-tokenize` at the L pin). Files and sha256s go in the record.
- **Cell value** = median (min..max) of the cell's requests. A single-request cell is reported as that one value.
- **Decode** = `predicted_per_second`; **prefill** = `prompt_per_second`, with client TTFT beside it.

**DSpark measurements:** decode, the server's draft acceptance (accepted / drafted) and mean accepted length, from
`/completion` timings or the server log, whichever this build prints.

**4 GiB ballast (U4g, L4g).** `ballast.cu` (committed with the harness): it calls `cudaMemGetInfo`, then
`cudaMalloc`s and writes `free − 4,096 MiB` on the 3060, checks that free memory now reads 4,096 ± 64 MiB, and holds it
until killed. The server starts after that check, and the ballast is killed after the cell. The server's own CUDA
context counts inside the 4 GiB, as it would on a 4 GB card. **Label: "fits in 4 GiB" (yes / no, with the failing
allocation line on a no). It is not a 4 GB card speed figure:** the 3060's bandwidth and SMs are all still there.
Decode and prefill under the ballast are recorded but are not compared with any 4 GB card. The GTX 1650 is not part of
this lock (a possible later exploratory arm).

**Order:** machine state → gates I6.1-I6.4 → L → L-d → L4g → U → U-ub2048 → U-d → U4g → Q-cmoe → Q-best → S10 →
S10-greedy → S10max → S10-split → smoke test (I7). Each arm starts a fresh server. The file is pre-read into page cache
before each llama.cpp arm.

## I6. Gates and per-cell checks

1. **Lock published:** this file is committed, pushed and mirrored byte-exact through the leak gate, and the public
   copy's sha256 equals the lock's before any measured request.
2. **Hashes:** every working copy matches I3 on the day. A mismatch stops the run.
3. **Builds:** L at the pin (`rev-parse`), U and S asset hashes as in I4. The load log shows `inkling2_loop` and no
   `check_tensor_dims` error.
4. **Correctness gate (every llama.cpp configuration that produces a speed figure), before its speeds count.**
   - **Text:** wikitext-2-raw-v1 `wiki.test.raw`, fetched with the pin's `scripts/get-wikitext-2.sh`, sha256 recorded.
   - **Reference PPL:** the L build's `llama-perplexity`, CPU only (`CUDA_VISIBLE_DEVICES=""`), f16 KV, `-c 4096
     --chunks 4 -t 4`, on the Inkling file. It must be finite and ≤ 15.0, or the run stops and Mark is told.
   - **Per configuration:** the same command on the GPU with that configuration's exact settings (build, `-ngl 99
     -cmoe`, q8_0 or f16 KV as run, `-fa auto`, ubatch).
   - **Pass:** the PPL is finite and within **±2.0% of the reference PPL**.
   - **Fail:** the configuration's speed cells are reported as "does not compute this model correctly at this setting",
     never as speeds. Issue #32830 (open; garbled output on hybrid offloading) and #32710 (open; NaN perplexity on
     CUDA) are the failure modes this catches.
   - **Configurations:** L and U (each also with `-ub 2048` if U-ub2048 or a fallback uses it), and Q-cmoe against
     its own CPU reference by the same rule. The DSpark arms reuse their base configuration's gate: the drafter does
     not change the target's logits, and the smoke test covers the output.
   - **Not covered:** 4,096-token chunks do not reach the 64K-256K regime. That is a stated limit (I10).
5. **FA state:** recorded from each load log: flash attention enabled or not, the CUDA0 compute-buffer size, the KV
   buffer sizes and the CUDA0 model buffer (K2, K3, K21). An "FA on" statement comes from the log, never from the flag.
6. **Per cell, logged:**
   - `free -m` and `swapon --show` before and after;
   - `/proc/vmstat` `pswpout` delta;
   - minimum MemAvailable (memwatch);
   - server VmRSS split into RssAnon / RssFile;
   - peak card memory.used (1 s poll), plus memory.used after `/health` and before the cold request;
   - PCIe gen/width during prefill;
   - NVMe read bytes during decode;
   - prompt_n and cache_n per request;
   - the first 200 characters of each answer.
7. **Memory guard:** `memwatch.py` v3 from the Strata records, unchanged (trips under 2 GiB MemAvailable, SIGTERMs the
   harness and every process named exactly `llama-server` or the Strata engine process name, which is recorded when
   the harness is written, then writes `TRIPPED`). A trip ends the arm and is reported. The arm script kills its own
   process tree on stop.

**Void rules.** A cell is void if any of its requests has:
- **swap-out above 0** (pswpout delta > 0);
- prompt_n spread over 3 tokens across the cell, or off target by more than 1%;
- cache_n above the template header;
- the PCIe link below gen 3 x16 during prefill;
- over 1 GiB of NVMe reads during decode;
- an empty answer, or one token repeated for more than half of the 256.

A void cell is re-run once (fresh server, its own cold request). Void twice is reported as void.

## I7. Smoke test (the only quality check)

On L (if its gate passed), U and S10, at 8K, temperature 0, reasoning default, `max_tokens 2048`. Scored on the final
answer (after any thinking block):
1. "A shop sells pens at $3 each and notebooks at $7 each. Maria buys 4 pens and 3 notebooks and pays with a $50 note.
   How much change does she get? Put only the number on the last line." Pass: last line = 17.
2. "Write a Python function `is_palindrome(s)` that ignores case and non-alphanumeric characters. Reply with only the
   code." Pass: the extracted function passes `is_palindrome("A man, a plan, a canal: Panama")`, `is_palindrome("")`,
   `not is_palindrome("hello")`, `is_palindrome("No 'x' in Nixon")`, `not is_palindrome("ab")`.
3. "Return only JSON with keys name (string), year (integer) and tags (array of exactly 3 strings) describing the Eiffel
   Tower's completion." Pass: it parses, year = 1889, and tags has 3 strings.
4. "What is the capital of Australia? Answer in one word." Pass: "Canberra" (case-insensitive, punctuation stripped).
5. Two turns: "My name is Ada and my favourite number is 42." then "What is my favourite number plus 8? Answer with the
   number only." Pass: 50.

An answer that hits the token cap inside thinking is a fail, recorded as "cap inside thinking" (TML warns of
repetitive reasoning). Smoke results are reported per runtime. For S10, which has no perplexity gate, 2 or more fails
mark its speed figures "output unverified". For L and U the I6.4 gate decides, and smoke results are reported beside it.

## I8. Predictions

**Codacus's, as reference points (his 3060, his unspecified 4-bit file, his build of the day):** K1 L at 256K does not
load; K4 U at 256K loads; K5 U decode ~18 at 8K and at 256K; K6 U prefill ~175, >300 at a bigger batch; K7 U VRAM ~3 GB
at 32K, ~3.5 GB at 64K, ~7.5 GB at 256K; K9 ~17 GB of RAM; K10 Qwen ~45 tok/s; K11 Qwen 256K in ~6 GB; K14 S10 ~35
tok/s; K15 S10 tops out at 16K; K18 U-d 20 → 18, ~40% acceptance; K19 Strata's drafter idle at the model's sampling.

**Ours (written 2026-11-24, before any build or measurement):**
- P1: L fails to load at 256K (with K1). L loads at 8K.
- P2: U loads at 256K (with K4).
- P3: U decode at 8K short: **14-20 tok/s**. Our Qwen `-ncmoe 40` (all experts on host) figure on this card was 28.1,
  and Inkling reads ~5.4B effective weights per token against ~3B, so we expect roughly 28 × 3 / 5.4.

### A1.1 Question

**The hypothesis comes from the Rushuna record's discussion.** With every expert in system RAM, Inkling decode is bound
by RAM read bandwidth. Layers 6-17 each run three passes, and each pass routes again. That makes 1.784 GB of
routed-expert reads per token, against 0.924 GB for one pass per layer.

On Rushuna, U-8k short decoded **10.41 tok/s**. That is 18.6 GB/s of routed-expert traffic, or 69% of the box's
**26.94 GB/s** `stream_read.c` read (4 threads, median of 3).

Tamanna reads ~1.56x that bandwidth with the same kernel, from its records: 41.95-42.44 GB/s at DDR4-3000, 4 threads.
**If decode scales with bandwidth, Tamanna's U-8k should land near 10.41 × (BW_Tamanna / BW_Rushuna).**

The test holds everything fixed that can be held fixed:
- the same binaries by sha256;
- the same files and flags, including `-t 4`;
- the same prompts, sampling and gate.

The rig changes. **Confounds that can't be removed:**
- **GPU:** the 3090 is faster at the on-card share of decode (attention and the dense and shared weights).
- **CPU:** the 5700X has more cache, and its memory latency differs.
- **PCIe 4.0 x16** (Rushuna is 3.0 x16).

The first confound pushes Tamanna above pure bandwidth scaling. So a result above the band says the GPU share was not
negligible on Rushuna. A result below it says something other than bandwidth limits decode, such as CPU compute or
latency.

### A1.6 Predictions (written 2026-11-25, before any Tamanna step)

**Provisional numbers use BW_Tamanna = 42.1 GB/s**, the figure on record. **The scored band is recomputed from the

- (a) bandwidth;

because it changes RAM speed with the same CPU.
